ADR-0018 – Explicit, Capability-Gated and Mutation-Safe Live Smoke Matrix

- **Contesto**: la Provider Layer ha consegnato quattordici scenari live per Ollama e llama.cpp. Eseguirli come normali test renderebbe la suite dipendente da server, modelli, rete e hardware locali; usare i default localhost degli adapter produrrebbe inoltre tentativi impliciti. Lifecycle e acquisition possono mutare residenza e catalogo, mentre supporto strutturale e disponibilità operativa hanno semantiche differenti.
- **Decisione**: `maestro bench smoke` esegue un provider esplicito per report e carica endpoint e modelli esclusivamente dalle variabili dichiarate nel manifest. In assenza del base URL il provider non viene costruito e gli scenari sono `skipped` senza I/O. Ogni scenario effettua capability introspection: supporto assente diventa `unsupported`, availability assente diventa `skipped`, availability unknown consente il probe. I modelli sono configurati per ruolo. Acquisition richiede la mutation guard esatta, verifica tramite discovery che la fixture non esista e rimuove soltanto una fixture acquisita dalla run. Stream, lifecycle, policy e observer affidano il cleanup garantito al runner. Il report JSON `1.1.0` registra la mappa dei modelli per ruolo ed è scritto atomicamente con permessi `0600`. I fallimenti diventano exit non-zero soltanto quando viene richiesto `--fail-on-failure`.
- **Conseguenze positive**: la suite deterministica resta offline; nessuna connessione localhost è implicita; unsupported, unavailable e failure non vengono confusi; modelli preesistenti non vengono rimossi; cleanup e redazione sono uniformi sui due adapter; lo stesso comando funziona come raccolta informativa o gate esplicito; ogni report descrive una sola configurazione provider con tutte le fixture usate.
- **Conseguenze negative e trade-off**: Ollama e llama.cpp richiedono run distinte; availability unknown può ancora produrre un errore live; tool calling e structured output dipendono dal comportamento reale del modello; il runner non supervisiona l'avvio dei server; una fixture lifecycle configurata in modo errato può essere scaricata dal cleanup; il controllo sulla fixture acquisition non elimina mutazioni concorrenti effettuate da processi esterni.
- **Alternative considerate**: test di integrazione obbligatori, connessione automatica ai default localhost, un report multi-provider, assenza di introspection preflight, unavailable trattato come failure, skip di availability unknown, pull/remove senza guard, rimozione incondizionata di fixture preesistenti, report con API key o prompt diagnostici, output scritto direttamente sul file finale e failure exit sempre obbligatorio.
