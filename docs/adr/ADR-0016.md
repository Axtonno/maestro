ADR-0016 – Additive Provider-Neutral Advanced Generation Baseline

- **Contesto**: il futuro Agent System richiede sampling controllabile, output JSON e un ciclo tool call/result comune. Ollama e llama.cpp offrono primitive simili con payload diversi: Ollama usa `format`, oggetti arguments e tool result per nome; llama.cpp usa Chat Completions, `response_format`, arguments serializzati e call ID. Esporre direttamente uno dei due protocolli legherebbe il core al provider e renderebbe incoerente lo streaming.
- **Decisione**: `CompletionRequest` riceve opzioni comuni, output strutturato, tool definitions e tool choice opzionali. `Message` rappresenta tool call complete e risultati riferibili per ID e nome; `StreamChunk` espone delta indicizzati con frammenti di arguments. Schemi e arguments completi usano `json.RawMessage` e devono essere oggetti JSON validi. Temperature e `top_p` sono puntatori per preservare sia il default sia lo zero valido; `MaxTokens=0` resta unset. Il Runtime e gli adapter validano localmente prima dell'I/O. Il terminale di output strutturati e tool streammati viene validato sintatticamente. Structured output e tool definitions sono mutuamente esclusivi nella baseline. Ollama supporta tool choice auto/none; llama.cpp traduce anche required/named. Gli adapter dichiarano supporto strutturale e availability conservativa tramite capability introspection.
- **Conseguenze positive**: le richieste semplici mantengono comportamento e firme; i due adapter eseguono gli stessi scenari JSON e tool loop; il core non dipende da tipi SDK; tool result e stream possono attraversare il Runtime senza perdere identità; combinazioni invalide falliscono senza I/O; opzioni proprietarie restano fuori dal contratto.
- **Conseguenze negative e trade-off**: aggiungere campi a struct pubbliche richiede composite literal con chiavi per la compatibilità sorgente futura; Maestro verifica la sintassi JSON ma non implementa JSON Schema; gli stream strutturati conservano una copia temporanea del contenuto; tool choice required/named non è disponibile sull'endpoint nativo Ollama; la reale affidabilità dipende dal modello, dal chat template e dalla versione del server; ID può essere vuoto per provider che non lo assegna.
- **Alternative considerate**: tipi request separati per ogni provider, mappe generiche di opzioni, dipendenza dai tipi OpenAI, esecuzione automatica dei tool nel Provider Runtime, buffering completo di ogni stream, tool calls soltanto non-streaming, schema come `map[string]any`, supporto di tutte le opzioni proprietarie e combinazione senza restrizioni tra grammar e tools.
