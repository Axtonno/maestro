ADR-0023 – Pre-Start Trusted In-Process Plugin System with Core-Owned Lifecycle

- **Stato**: Accepted.
- **Contesto**: la baseline Plugin Runtime implementa già plugin basati su `runtime.Component`, un catalogo di loader trusted in-process, registrazione nel Registry globale ed eventi. La Milestone 5 deve stabilizzare questo confine senza duplicare identità, stato, dependency graph o lifecycle e senza anticipare distribuzione esterna, permission model e Context Engine. I termini available, registered, loaded e running devono inoltre avere semantiche non sovrapposte.
- **Decisione**: un plugin continua a essere un `runtime.Component`; `runtime.Metadata` resta l'unica fonte per ID, nome, versione, dipendenze e capability, mentre `plugin.Manifest` dichiara esclusivamente la versione esatta dell'API Plugin Runtime richiesta. `plugin.Runtime` conserva le firme pubbliche esistenti. Non vengono introdotti descriptor di catalogo o un contratto workspace framework-neutral finché un consumer concreto non ne definisce i dati necessari.
- **Decisione**: `Available` elenca loader collegati alla build, `Registered` e `Has` descrivono istanze presenti nel Registry plugin, un evento `plugin.loaded` descrive il completamento riuscito dell'operazione factory più registrazione e lo stato operativo resta esclusivamente nello `runtime.StateManager`. Non esiste uno stato persistente `loaded` separato. Gli ordini di listing riflettono le registrazioni riuscite e non costituiscono ranking o selezione implicita.
- **Decisione**: loader e plugin sono codice Go fidato eseguito in-process con i privilegi di Maestro. Il loader viene invocato senza lock interni, costruisce soltanto l'istanza e non registra, avvia o acquisisce risorse longeve. `Load` valida context, risultato, identità e manifest e delega la registrazione al Runtime Core. Errori sentinel e cause restano ispezionabili tramite `errors.Is`; una failure non rende il plugin visibile nel registry dedicato e non emette eventi di successo per gli stadi non completati.
- **Decisione**: caricamento e registrazione sono supportati prima di `Runtime.Start`. Il Runtime Core resta proprietario del vincolo temporale, del dependency graph, dello stato e del lifecycle. Gestor scopre i plugin una sola volta attraverso il Registry globale dei componenti; la registrazione invalida lo snapshot tramite il wiring esistente e il refresh resta esplicito. Il Plugin Runtime non possiede una source Gestor dedicata e non invoca capability lifecycle.
- **Decisione**: gli eventi plugin sono notifiche sincrone best-effort pubblicate dopo lo stato corrispondente e fuori lock. Errori e panic dell'Event Bus vengono isolati al confine Plugin Runtime affinché non alterino un'operazione già completata; un subscriber lento continua ad applicare backpressure secondo ADR-0005. Il payload contiene ID e, dopo l'istanza, un riferimento trusted in-process che non deve essere trattato come envelope telemetrico serializzabile.
- **Decisione**: packaging, installazione, firme, provenance, marketplace, shared object, process isolation, sandbox, permission model, unload, hot replacement e registrazione durante l'esecuzione sono fuori dal gate della Milestone 5. Packaging e plugin di terze parti appartengono alla Milestone 8; il permission model operativo appartiene alla Milestone 7.
- **Conseguenze positive**: API pubblica minimale e già compatibile; una sola identità e una sola state machine; graph e lifecycle coerenti; discovery capability senza duplicazioni; caricamento deterministico e verificabile con test offline; evoluzioni di distribuzione future possono alimentare il contratto `Loader` senza modificare registry e lifecycle.
- **Conseguenze negative e trade-off**: un'applicazione deve collegare e registrare esplicitamente i loader; i metadata del plugin non sono disponibili prima dell'istanza; il catalogo non può essere trattato come marketplace; non esiste hot loading; un loader malevolo o difettoso opera con i privilegi del processo; consumer framework-neutral futuri potrebbero richiedere un'estensione additiva del contratto.
- **Alternative considerate**: duplicare i metadata nel manifest o in descriptor di catalogo, introdurre uno stato plugin autonomo, assegnare lifecycle e graph al Plugin Runtime, creare una source Gestor plugin, caricare automaticamente tutti i loader, consentire registrazioni durante l'esecuzione, definire subito un'API workspace generica, usare shared object Go, processi esterni o WebAssembly nella Milestone 5.
