ADR-0025 – Bounded Agent Sessions with Atomic Permission-Gated Effects

- **Stato**: Accepted.
- **Contesto**: Provider Runtime espone tool calling provider-neutral e Context Engine produce bundle workspace-aware, ma Maestro non possiede ancora contratti per tool eseguibili, autorizzazioni, sessioni, piani o loop agente. Gli arguments prodotti dal modello sono input non fidati; una decisione `allow` pubblicamente fabbricabile non può diventare autorità sufficiente per produrre effetti.
- **Decisione**: Tool System e Agent System sono package pubblici separati: `pkg/tool` non importa `pkg/agent`; `pkg/agent` coordina contratti Tool, Provider e Context senza modificare `pkg/runtime.Runtime`. Le implementazioni concrete future vivono in `internal/tool` e `internal/agent`; il composition root verrà esteso soltanto nella Fase 7.
- **Decisione**: il percorso tool è `Prepare -> authorize -> Execute`. `PreparedInvocation` lega tool ID/versione, call ID, run ID, arguments JSON canonicalizzati, action e fingerprint SHA-256. Tutte le action vengono autorizzate atomicamente; non esiste esecuzione parziale implicita. L'API pubblica `Runtime.Invoke` incorpora autorizzazione ed esecuzione e non accetta `Decision` o grant dal chiamante.
- **Decisione**: `Decision` e `Approval` sono descrizioni pubbliche, non permit. Il permit operativo è un dettaglio interno non fabbricabile dal modello, dall'agente o dal tool: è emesso da un'autorità posseduta dal Tool Runtime, vincola run ID e permission fingerprint e viene verificato e consumato dall'executor. La Fase 2 implementa controllo e issuer deterministico di test; la Fase 3 implementa policy, Approver e grant reali.
- **Decisione**: policy ID è sempre esatto e non esiste un default permissivo. Nessuna regola applicabile significa deny; `prompt` senza Approver non significa allow. I grant one-shot vengono consumati atomicamente; i grant run-scoped sono legati a run ID e fingerprint, non si estendono per prefisso e non sopravvivono al run o al processo.
- **Decisione**: permission deny è classificato dal permission model come recuperabile o terminale, indipendentemente dal testo del modello. Un deny recuperabile può diventare tool result entro i budget; un deny terminale chiude il run. Tool con più action ricevono una sola decisione atomica.
- **Decisione**: `model.invoke` e `model.disclose` usano lo stesso permission model ma una `PermissionRequest` con subject `model`, non una tool invocation fittizia. Il Context Engine costruisce localmente il bundle; Maestro deriva un `DisclosureManifest` redatto e un fingerprint; autorizza atomicamente invocazione e disclosure; soltanto dopo può chiamare il Provider Runtime. Provider e modello restano input esatti del run.
- **Decisione**: ogni run ha un unico coordinatore attivo. Gli snapshot di sessione sono immutabili e leggibili concorrentemente; un run terminale non può essere riusato o avviato una seconda volta. Piani e step hanno transizioni validate, dipendenze acicliche e versioni monotone. Sessione e piano iniziali sono bounded e in-memory.
- **Decisione**: prima del commit terminale, cause concorrenti usano la precedenza `deadline > canceled > limit > permission_denied > blocked > provider_failure > tool_failure > planning_failure > internal_failure > completed`. Dopo il primo commit il terminale è immutabile e nessuna causa tardiva lo sostituisce.
- **Decisione**: ogni run dichiara hard ceiling positivi per durata, turni modello, tool call totali/per turno, step, revisioni, byte di risultato/sessione e token input/output. Il modello non può aumentare i limiti. Tool mutanti non vengono ritentati implicitamente.
- **Decisione**: una action `workspace.mutate` rende il contesto stale quando l'esecuzione inizia, anche se il tool termina con errore, cancellazione o esito ambiguo. Soltanto un refresh esplicito e riuscito del Context Engine rende corrente una nuova generazione.
- **Decisione**: gli eventi usano allowlist strutturali esatte. Gli eventi tool possono contenere soltanto run ID, tool ID, call ID, action count, decision kind, deny disposition, outcome, truncated, duration e failure code. Gli eventi agent possono contenere soltanto run ID, agent ID, step ID, state, step state, terminal reason, plan version, contatori di turni/tool/token, durata e failure code. Provider, modello, policy, workspace, resource, prompt, piano testuale, path, arguments, output, permit ed error string sono esclusi.
- **Conseguenze positive**: confine esplicito tra proposta e autorità; permission default-deny; invocazioni content-bound; sessioni e terminali deterministici; contratti provider- e framework-neutral; nessuna dipendenza inversa dal Tool System all'Agent System; osservabilità redatta per costruzione.
- **Conseguenze negative e trade-off**: più value object e validazione prima dell'esecuzione; policy e target devono essere configurati esplicitamente; deny e terminal races richiedono semantica applicativa; il runtime in-process trusted non isola implementazioni Go malevole; il Context Engine può richiedere refresh aggiuntivi dopo mutazioni ambigue.
- **Alternative considerate**: passare `Decision{Allow:true}` a `Execute`, esporre un costruttore pubblico di permit, autorizzare il solo nome del tool, consentire action parziali, usare il primo policy/provider/model registrato, rappresentare il modello come tool, autorizzare la disclosure prima di costruire il manifest, riusare sessioni terminali, lasciare il loop senza ceiling e affidare redazione o permission semantics al prompt.
