ADR-0006 – Capability-Based Provider Runtime

- **Contesto**: Maestro deve orchestrare provider differenti senza trasferire nel Runtime Core dettagli di Ollama, llama.cpp o servizi remoti. Non tutti i provider espongono le stesse operazioni: alcuni completano conversazioni, altri supportano anche streaming, embedding o discovery dei modelli.
- **Decisione**: il layer pubblico `pkg/provider` rimane indipendente dal Runtime Core. `Provider` descrive soltanto l'identità; `Completer`, `Streamer`, `Embedder` e `ModelLister` sono capability opzionali. Un Provider Runtime thread-safe registra e risolve i provider, seleziona un default esplicito e inoltra le operazioni senza mantenere lock durante il codice del provider. Lo streaming usa un contratto pull-based con chiusura esplicita.
- **Conseguenze positive**: provider sostituibili, supporto naturale a insiemi diversi di capability, nessuna dipendenza da SDK esterni nel core, routing deterministico e responsabilità chiare per concorrenza e lifecycle degli stream.
- **Conseguenze negative e trade-off**: il chiamante deve gestire esplicitamente lo stream e verificare gli errori di capability non supportata; retry, fallback e bilanciamento non sono impliciti.
- **Alternative considerate**: un'unica interfaccia provider monolitica, canali Go gestiti dal Runtime per lo streaming, selezione automatica del primo provider registrato e integrazione diretta dei singoli SDK nel Runtime Core.
