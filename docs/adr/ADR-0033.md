# ADR-0033 – Modalità di interazione separate per Direct Chat e Verified Agent

- **Stato**: Accepted.
- **Data**: 2026-08-27.
- **Contesto**: la Milestone 13 ha concluso che il reference agent read-only non converge stabilmente sul profilo osservato per analisi multi-file, mentre una completion con un file allegato direttamente può rispondere correttamente. L'attuale CLI espone soltanto `maestro run`, costruisce sempre il composition graph agentico e usa un solo modello e timeout. Confondere completion diretta e agent loop impedirebbe di attribuire correttamente qualità, latenza, disclosure e failure.
- **Decisione**: Maestro espone due modalità read-only distinte. `maestro chat` riceve contesto selezionato esplicitamente e invoca una sola completion senza tool, retrieval, index, state machine, sessione, approver o fallback. `maestro agent` è il nome canonico del percorso verificato e conserva Context Engine, tool read-only, permission runtime, evidence binding, choreography e stop rule.
- **Decisione**: `maestro run` resta un alias esatto e deprecato di `maestro agent` per tutta la serie v0.3.x. Alias e comando canonico condividono parser, application path, output, exit code e test; l'alias non cambia autorità e non può degradare a chat. La deprecazione è documentale e nella help durante la Milestone 14; nessuna riga aggiuntiva viene iniettata nell'output stabile di una run. La sua eventuale rimozione richiede una nuova ADR e non avviene prima di v0.4.0.
- **Decisione**: la sintassi candidata è `maestro chat [--config path] [--file logical-path] [--stream] [question]`. La domanda è un unico positional composto dai token residui oppure, quando assente, viene letta da stdin con lo stesso limite di 1 MiB del percorso agentico. Domanda vuota, flag duplicati o positional e stdin concorrenti falliscono prima della composition. `--file` è opzionale e singolo; non accetta glob, directory, path assoluti o selezione automatica. `--stream` è opt-in e resta disabilitato finché la matrice di equivalenza della Fase 4 non è verde.
- **Decisione**: un file chat è un path logico relativo sotto il workspace configurato. Il loader rifiuta componenti vuoti, `.`, `..`, backslash, NUL, symlink in qualunque componente, file non regolari, contenuti oltre il limite, UTF-8 invalido, NUL e cambi di identità o contenuto durante la lettura. Il file viene aperto tramite confinement filesystem e riletto/verificato prima della disclosure. Il path fisico non entra in prompt, output operativo o report.
- **Decisione**: assenza di `--file` è uno stato valido e non attiva retrieval. La completion riceve un'istruzione epistemica esplicita che dichiara assente il contesto workspace e vieta di inventare fatti sul progetto. Una risposta vuota o non finale è un failure; non viene sostituita con output deterministico e non avvia il verified agent.
- **Decisione**: domanda, path logico e contenuto non fidato sono messaggi o sezioni delimitate e non ambigue. Il contenuto workspace è dati non attendibili e non può modificare autorità, configurazione o tool. La request chat dichiara zero tool e `tool_choice: none`; una response contenente tool call è invalida anche se il provider la restituisce.
- **Decisione**: lo schema candidato è `version: 2` e introduce profili `interaction.chat` e `interaction.agent` distinti. Ogni profilo dichiara almeno modello, timeout, streaming, `num_ctx` e `thinking`; chat dichiara inoltre limiti bounded per file e output. `thinking` è una enum tri-state `default`, `true`, `false`, non un boolean con zero-value implicito. I file v1 continuano a essere accettati per `maestro agent` e `maestro run` tramite semantica v0.2.0 invariata, ma `maestro chat` li rifiuta con `chat_profile_required`. Non esiste conversione implicita da `models.chat` al profilo direct chat.
- **Decisione**: `num_ctx` e `thinking` entrano nella request provider-neutral. Un valore esplicito deve essere mappato esattamente o il preflight fallisce con capability non supportata; non sono ammessi ignore o fallback. Valore richiesto, valore effettivo quando attestabile, truncation, token e latenza sono osservabili senza serializzare prompt o response. `unknown` resta distinto da un valore confermato.
- **Decisione**: il servizio chat dipende soltanto da configurazione chat validata, workspace root confinata, clock e capability provider di completion/streaming. Non riceve Agent Runtime, Tool Runtime, Context Engine, Gestor index, policy/approver o callback di fallback. Il composition root chat può condividere adapter e client provider, ma non l'application graph agentico.
- **Decisione**: su successo stdout usa un envelope stabile con modalità, terminale, metadati redatti, marker `result` e contenuto finale richiesto. stderr è riservato a failure sintetici. Input/config/path invalidi usano exit code 2; capability, modello, provider o deadline provider usano 4; cancellazione usa 130; risposta invalida, hard limit o failure interna usano 1. I reason code iniziali sono `invalid_request`, `chat_profile_required`, `file_not_allowed`, `provider_unavailable`, `capability_unsupported`, `deadline_exceeded`, `canceled`, `response_invalid`, `limit_exceeded` ed `execution_failed`.
- **Decisione**: la Milestone 14 è development-only. `maestro chat`, schema v2 e i nuovi profili non ampliano la compatibility promise v0.2.0 e non entrano in un artifact supportato prima della qualificazione della Milestone 15. Controlled Mutation, shell, Git, processi, session memory, multi-file automatico e multi-agent restano fuori scope.
- **Conseguenze positive**: latenza e qualità della completion diretta possono essere misurate separatamente dalla capacità di esplorazione; disclosure e autorità sono minime e verificabili; configurazioni legacy non acquisiscono nuove semantiche; l'agent mantiene invarianti e compatibilità.
- **Conseguenze negative e trade-off**: lo schema v2 e il nuovo comando aumentano la superficie da testare; `run` e `agent` restano duplicati nominalmente durante la migrazione; provider che non attestano le opzioni richieste possono essere esclusi dal profilo chat anche se sanno completare; la modalità single-file non risponde a domande che richiedono discovery.
- **Alternative considerate**: aggiungere `--direct` a `maestro run`, usare chat come fallback dopo un timeout agentico, riutilizzare implicitamente `models.chat` dei file v1, consentire più file o glob, costruire l'intero application graph e non invocarlo, ignorare `thinking` non supportato, produrre una risposta locale senza qualificare il modello. Tutte renderebbero meno osservabili semantica, disclosure o attribuzione dei failure.
