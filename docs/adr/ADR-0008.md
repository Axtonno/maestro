ADR-0008 – Trusted In-Process Plugin Catalog

- **Contesto**: per chiudere il Plugin Runtime serve un percorso di caricamento e discovery, ma i shared object Go richiedono identità di toolchain e dipendenze e non costituiscono un confine di sicurezza. Maestro non dispone ancora di un permission model per codice di terze parti.
- **Decisione**: il Plugin Runtime mantiene un catalogo thread-safe di `Loader` associati a ID stabili. I loader sono factory in-process eseguite senza lock interni e possono essere implementate anche da package esterni. Ogni plugin dichiara nel `Manifest` la versione esatta dell'API Plugin Runtime; il caricamento valida contesto, risultato, corrispondenza dell'ID e compatibilità prima di delegare la registrazione al Runtime Core. I loader collegati al processo sono considerati codice fidato. Le operazioni riuscite sono osservabili tramite listing deterministici ed eventi sul bus condiviso.
- **Conseguenze positive**: discovery e caricamento deterministici, cancellazione esplicita, nessuna dipendenza esterna, compatibilità verificata prima del lifecycle e un'estensione futura possibile senza accoppiare il registry a un formato di distribuzione.
- **Conseguenze negative e trade-off**: installazione di pacchetti, firme, sandbox, process isolation, unload e hot replacement non sono forniti; un loader malevolo dispone degli stessi privilegi del processo Maestro.
- **Alternative considerate**: package standard `plugin`, scansione automatica di directory, download implicito, processi plugin obbligatori, WebAssembly e registrazione senza catalogo.
