ADR-0007 – Component-Based In-Process Plugin Runtime

- **Contesto**: Maestro deve distinguere i plugin dagli altri componenti senza duplicare il dependency graph e il lifecycle già posseduti dal Runtime Core. Il caricamento dinamico di binari Go introduce inoltre vincoli di compatibilità, piattaforma e fiducia che non sono ancora stati definiti.
- **Decisione**: un `Plugin` è un `runtime.Component` registrato attraverso un Plugin Runtime dedicato. Il Plugin Runtime mantiene l'indice dei plugin e delega la registrazione al Runtime Core; configurazione, inizializzazione, avvio, arresto e ordinamento delle dipendenze restano quindi responsabilità del lifecycle esistente. Il primo incremento supporta plugin Go collegati staticamente e registrati in-process. Discovery, installazione e caricamento di artefatti esterni sono separati dal contratto di registrazione e rinviati a una decisione successiva.
- **Conseguenze positive**: una sola state machine, un solo grafo delle dipendenze, plugin interoperabili con tutti i componenti, API minimale e nessun vincolo prematuro sul formato di distribuzione.
- **Conseguenze negative e trade-off**: i plugin del primo incremento devono essere disponibili al processo in fase di build; la classificazione come plugin dipende dal percorso di registrazione e non dal solo tipo strutturale; non sono ancora disponibili unload e hot install.
- **Alternative considerate**: lifecycle indipendente per i plugin, duplicazione dei metadati plugin, uso immediato del package standard `plugin`, caricamento di processi esterni e trattamento indistinto di ogni componente come plugin.
