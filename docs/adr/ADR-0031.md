# ADR-0031 – Contratto Controlled Mutation v0.2.0

- **Stato**: Accepted.
- **Contesto**: la Milestone 9 ha chiuso l'osservazione della v0.1.x e ha dato GO alla Milestone 10. La baseline possiede già read-before-patch, fingerprint SHA-256, permission default-deny, permit one-shot, digest precondition, containment con `os.Root`, rifiuto dei symlink e refresh del Context Engine. Non possiede ancora un oggetto patch unico per preview e apply; il terminale non mostra la diff concreta; il profilo sperimentale consente un grant mutativo run-scoped; la sostituzione di un file esistente tronca e riscrive la stessa handle e non garantisce commit atomico. La presenza di questi componenti non costituisce supporto mutativo.
- **Decisione**: la sola unità mutativa candidata della v0.2.0 è un tentativo di `workspace.patch` su un unico file esistente. Ogni run può tentare una sola mutazione. Il tool sostituisce una sola occorrenza testuale esatta e non crea, elimina, rinomina o coordina file. `workspace.write` resta sperimentale e fuori dalla compatibility promise.
- **Decisione**: il percorso supportato del reference agent Laravel accetta soltanto file regolari UTF-8 senza NUL sotto il path logico normalizzato `app/**/*.php`, con stato iniziale e finale non superiori a 2 MiB. Sono esclusi root assolute, `.` e `..`, backslash, path hidden, symlink in qualsiasi componente, file fuori da `app/`, file non PHP, file mancanti, directory, device e contenuti binari. Root fisiche e path host non entrano nella proposta o nella preview.
- **Decisione**: una read riuscita, non troncata e verificata deve precedere la patch. La preparazione costruisce un oggetto immutabile autorevole contenente tool e versione, run e call, path logico, digest atteso, testo esatto da sostituire, testo sostitutivo, contenuto risultante bounded, action, intenzione sintetica deterministica e diff. Preview, permission fingerprint ed Execute derivano esclusivamente da questo oggetto; non vengono rigenerati da prompt o stato modello dopo l'approvazione.
- **Decisione**: la preview precede sempre la richiesta di approval e mostra soltanto tool, intenzione sintetica, path logico, digest atteso, precondizioni e diff bounded del file interessato. Non mostra root fisiche, secret, prompt, payload grezzi del modello, file estranei o contenuto invariato non necessario alla decisione. Se la preview non può essere costruita integralmente entro i limiti, la mutazione fallisce chiusa prima dell'approval.
- **Decisione**: ogni mutazione supportata richiede policy `workspace_mutate: prompt`, TTY interattivo e `allow once`. Non sono supportati policy `allow`, grant mutativi run-scoped, auto-approval, flag `--yes` o approver non interattivi. Deny, risposta vuota, EOF, no-TTY e input invalido producono `permission_denied`, exit code 3 e nessun inizio dell'effetto. Cancellazione o deadline durante l'approval non emettono authority e conservano il rispettivo terminale.
- **Decisione**: il fingerprint lega policy, tool ID e versione, run, call, arguments normalizzati e action e quindi anche path, digest e sostituzione concreta. `allow once` autorizza al massimo un tentativo di Execute e il permit viene consumato una sola volta. Qualsiasi variazione di proposal, tool/version, run/call, path, digest, diff o action richiede una nuova read, una nuova proposta e una nuova approval; il replay è rifiutato. Non esistono retry impliciti.
- **Decisione**: Execute rivalida immediatamente prima del commit path, tipo, symlink, digest, occorrenza e dimensione. Il nuovo contenuto viene scritto in un file temporaneo non seguibile nella stessa directory, sincronizzato e sostituisce il target tramite rename atomico; la directory viene quindi sincronizzata. I permessi del file regolare vengono preservati entro il profilo Linux supportato. Ogni failure prima del rename lascia il target byte-identico e tenta il cleanup del temporaneo. Il rename riuscito è il punto di commit: failure o cancellazione successive non possono descrivere il workspace come invariato e non causano rollback implicito.
- **Decisione**: l'inizio di Execute marca il contesto stale, anche se una precondizione o il commit falliscono. Dopo un commit riuscito l'Agent Runtime deve completare `Index` e `Build`, ottenere una generazione strettamente maggiore e un bundle corrispondente prima di accettare un testo finale del modello. Apply fallito termina senza successo; apply riuscito con reindex/build fallito termina `tool_failure` con failure code `context_refresh_failed`, `ContextStale=true` e stato applicativo che registra il commit. SIGINT o deadline prima del rename lasciano il file invariato; dopo il rename usano il terminale di cancellazione/deadline ma registrano che la patch è stata applicata e che il refresh non è completo.
- **Decisione**: il profilo candidato della Milestone 11 usa Linux `amd64`, Ollama e `ibm/granite4.1:8b`; il lower-bound hardware iniziale resta Intel Core i5-8365U, 8 CPU logiche, 15 GiB RAM e 4 GiB swap. Questo è un profilo candidato, non supportato: le evidenze storiche mostrano Gate A `3/3`, Gate B `2/2` e Gate C fallito per deadline. La Milestone 11 applicherà senza modifiche retroattive Gate A `3/3`, Gate B `2/2` e Gate C `3/3` e potrà concludere supporto sul profilo, requisito hardware superiore provato oppure rinvio della mutazione.
- **Decisione**: la configurazione mutativa è un file separato e opt-in che elenca `workspace.patch` e imposta `workspace_mutate: prompt`; il profilo distribuito v0.1.x resta byte-invariato con soli list/read/search e mutation deny. Lo schema YAML `version: 1`, la CLI, gli exit code e i package pubblici 0.x restano sperimentali ma intenzionali; l'oggetto concreto di proposta, il commit filesystem e i renderer vivono inizialmente sotto `internal/`. Eventuali cambi pubblici seguono l'audit 0.x e le note di migrazione.
- **Decisione**: shell, Git, Composer, Artisan, PHPUnit, processi, sandbox, recovery, rollback generale, memoria persistente, plugin/tool terzi, selezione automatica del modello, multi-agent, modifiche multi-file e policy mutative non interattive restano fuori scope. Il runtime continua a essere trusted in-process e opera con i privilegi dell'utente locale.
- **Conseguenze positive**: la decisione dell'utente è legata alla modifica effettivamente mostrata; il punto di commit e gli esiti prima/dopo commit sono espliciti; il profilo read-only non acquisisce autorità; la Milestone 11 riceve una superficie stretta e misurabile.
- **Conseguenze negative e trade-off**: il primo percorso mutativo è limitato ai file PHP sotto `app/`, a una patch e a un tentativo per run; un refresh fallito può lasciare una modifica applicata con contesto stale e richiede intervento manuale; rename e directory sync richiedono implementazione e fault injection specifiche del profilo Linux; il candidato modello può essere nuovamente escluso dal gate live.
- **Alternative considerate**: mostrare soltanto action/path senza diff, approvare il nome del tool, conservare grant run-scoped, consentire policy `allow`, riscrivere in-place, applicare più file, eseguire rollback automatico dopo failure di reindex, qualificare implicitamente `workspace.write`, scegliere un nuovo modello durante il gate o presentare la baseline hardware come già supportata. Queste alternative ampliano l'autorità, rendono ambigua la decisione o confondono implementazione deterministica e qualificazione live.
